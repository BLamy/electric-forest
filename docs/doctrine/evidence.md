# Evidence doctrine

{% hint style="warning" %}
A builder being satisfied is a **claim**. A deterministic recording of the run that
satisfied them is **evidence**. No task reaches `verified` on claims: a separate,
adversarial critic session must interrogate the evidence, hold it against the diff,
and fail to refute it.
{% endhint %}

## Two evidence layers

{% tabs %}
{% tab title="Stream layer" %}
Always present. Event-log dumps, state digests, replay determinism, convergence diffs.
A state-equality claim is a **digest comparison** over canonically encoded state —
`cmp` semantics, exact match — never an eyeball.
{% endtab %}
{% tab title="Browser layer" %}
For anything a user can reach: a [Replay](https://replay.io) recording of the final
happy run, interrogated by the critic through the Replay MCP. Not "trust me, I
checked" — here is the session where it worked, in full.
{% endtab %}
{% endtabs %}

## The roles

**Builder** — implements exactly one task from the top of the queue, self-validates as
much as it likes inside the task's `work/` folder, then submits the diff, a claim, and
recorded evidence of the final happy run.

**Critic** — a fresh session, never the one that implemented. It attacks from two
directions:

1. **Falsification** — find one point in the evidence where the program contradicts the
   claim or the acceptance criteria.
2. **Sufficiency** — find changed code the evidence never exercised. Unexecuted diff is
   either unproven or dead.

**Progress critic** — after every third failed run of one task, decides whether the loop
is converging or death-spiraling. Uncertain means stop.

## Rules that never bend

- Goldens are frozen, committed artifacts; a golden regenerated by the code under test
  at test time proves nothing.
- Status changes go through task frontmatter and `python3 tools/build_queue.py`; only a
  critic sets `verified`.
- No unchanged task shape may exceed ten verification runs. A failed run 10 triggers one
  atomic decomposition with a single three-run budget shared across its children.
- Verification-run accounting is durable and task-global: before any builder call, two
  fresh readers must return byte-identical output from the committed snapshot command.

{% expandable title="Why so adversarial?" %}
Because the product is the evidence layer. Durable streams that store every mutation as
an appendable, replayable event _are_ the recording. If the process that builds the
product could be greenwashed, the product's central promise — every session is a
trace you can interrogate — would be hollow.
{% endexpandable %}
